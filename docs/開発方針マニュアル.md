# 開発方針マニュアル

> このマニュアルは、**何を・どの順番で決め、何をまだ決めないか**を定めるものです。
> 具体的な内容(機能・画面・技術・データ)は、ここには書きません。それは各フェーズの成果物に書きます。

---

## 0. このマニュアルについて

### 何のためにあるか

開発でいちばん高くつくのは、**決める順番を間違えること**です。

- **後で決めればいいことを先に決める**と、その決定が間違っていたとき、積み上げたものを直すことになります。
- **先に決めるべきことを後回しにする**と、同じルールがコードのあちこちに複製され、変更のたびに複数箇所を直すことになります。

このマニュアルは、その2つを避けるための**順序表**です。

### 書かないこと

機能の一覧、画面の構成、使う技術、データの形。これらはすべて**成果物**の側に書きます。マニュアルが具体的な内容を持つと、プロジェクトごとに書き換えが必要になり、使い回せなくなります。

### 読む人

チーム全員。特に、開発のまとめ役を初めて務める人。専門用語には一言の補足を付けます。

## 1. 基本原則

| # | 原則 | 意味 |
|---|---|---|
| 1 | **「なぜ」から決める** | 目的が決まる前に、手段(機能・技術)を決めない |
| 2 | **人から始める** | 画面や技術ではなく、使う人の困りごとから考える |
| 3 | **順序は依存の順序** | 後ろの決定は前の決定に依存する。前を変えたら、後ろを見直す |
| 4 | **「まだ決めない」を決める** | 先送りは設計の一部。各フェーズで、決めないことを明記する |
| 5 | **決定は記録する** | 誰が・いつ・なぜ決めたか、却下した案は何か。後から辿れるようにする |
| 6 | **小さく貫通させてから広げる** | 最小の1操作を端から端まで通し、それから機能を足す |
| 7 | **整える変更と、変える変更を混ぜない** | 「動きを変えずに整える」PRと「動きを変える」PRは分ける |
| 8 | **実例で約束する** | 文章の約束より、実際のデータの例を正とする |
| 9 | **事実で語る** | 利用者像は想像で書かない。観察・聞き取り・自分の経験から書く |
| 10 | **価値で層を切り、技術は後から割り当てる** | 作る順序は、利用者に起きる変化で決める。技術の都合は、技術を選んだあとで足す |

## 2. 全体の流れ

```
P0  目的と制約
  ↓
P1  ロール
P2  ペルソナ        (仮説 → 事実で検証)
P3  ジャーニー
P4  ストーリー
  ↓
P5  要件            (スコープ・優先度・品質の順位・受け入れ条件)
                    + 権限・通知・個人情報を持つかの「有無」
  ↓
P6  業務フロー
P7  データ項目と状態 (用語集・状態遷移・見せ方のルール)
P8  画面設計         (情報設計: どのページに、何を載せるか。見た目は含まない)
  ↓
P9  層の設計         (価値の層。依存は機能・データの言葉で。技術は書かない)
P10 MVP の決定       (層のどこで切るか)
P11 拡張の余地の確認  (外側の層を塞いでいないか)
  ↓
P12 権限設計 / P13 通知設計   (P5 で「有り」とした場合だけ)
P14 見た目の設計
  ↓
P15 技術選定         ← ここで初めて技術名を出す(+ 実現性の確認)
P16 貫通             (外とのやり取りの形もここで決める)
P17 縦切りで機能追加
P18 品質確認
P19 運用と振り返り  ──→ このマニュアル自体を更新する

どのフェーズからでも、前のフェーズへ戻ってよい(§5 手戻りのルール)
事実集め(既存サービスの調査・聞き取り)は、P2〜P3 と並行して回す
```

**技術を決めるのは P15 です。** それより前に技術名が出てきたら、決めるのが早すぎないか疑ってください。

## 3. 各フェーズ

各フェーズは、次の項目で書きます。

- **目的**: なぜこのフェーズがあるか
- **決めること** / **決めないこと**
- **成果物**: 何を、どこに残すか(`dev_policy/` のファイル名は、フェーズ番号に合わせます)
- **終わりの判定**: これを満たしたら次へ進んでよい
- **よくある失敗**

### P0 目的と制約

- **目的**: 何のために作るかを、一言で言えるようにする。
- **決めること**
  - 作る理由
  - 成功の定義(あとで「できた」と判定できる形で)
  - 制約(期間・人数・予算・公開範囲・運用する期間)
  - 最終的に決める人
- **決めないこと**: 機能、画面、技術
- **成果物**: `dev_policy/00_目的と制約.md`
- **終わりの判定**
  - 3行で説明できる
  - 「やらないこと」が1つ以上書かれている
- **よくある失敗**: 目的が「〇〇を作る」という手段になっている。

### P1 ロール

- **目的**: このプロダクトに関わる人を、全員書き出す。
- **決めること**: 登場人物の一覧。画面を使わない人(準備する人、判断する人、引き継ぐ人、悪意のある人)も含める。
- **決めないこと**: その人たちの詳しい人物像、画面、機能
- **成果物**: `dev_policy/01_ロール.md`
- **終わりの判定**: 「ほかに関わる人はいないか」を、一度は問い直した。
- **よくある失敗**: 画面を使う人だけを数えてしまう。

### P2 ペルソナ

- **目的**: そのロールの人が、何に困り、何を恐れ、何を求めるかを、具体的に捉える。
- **決めること**: ロールごとの人物像(数行)。**事実で書く。** 事実がまだ無いものは「仮説」と明記し、検証方法を添える。
- **決めないこと**: 解決の手段
- **成果物**: `dev_policy/02_ペルソナ.md`
- **終わりの判定**: すべてのペルソナに、「事実」か「仮説(+検証方法)」の印がある。
- **よくある失敗**: 年齢や趣味など、想像で足した飾りを書く。作る側の願望を、利用者の声にしてしまう。

### P3 ジャーニー

- **目的**: その人が、時系列で何をして何を感じるか、どこで詰まるかを見つける。
- **決めること**: 時系列(使う前・使っている間・使った後)での行動と感情。**うまくいかなかった瞬間**を必ず集める。
- **決めないこと**: 詰まりの解決方法
- **成果物**: `dev_policy/03_ジャーニー.md`
- **終わりの判定**: 失敗の場面が、書かれている。
- **よくある失敗**: うまくいく流れだけを書く。

### P4 ストーリー

- **目的**: 詰まりの解決として、何ができれば嬉しいかを書く。
- **決めること**: 「〜として、〜したい。なぜなら〜」の形のストーリー
- **決めないこと**: 実現手段、画面、データ
- **成果物**: `dev_policy/04_ストーリー.md`
- **終わりの判定**: すべてのストーリーに「なぜなら」があり、ジャーニーの詰まりのどれかに結びついている。
- **よくある失敗**: ジャーニーを見ずに、思いついた要望を書く。

### P5 要件

- **目的**: 「何を作るか」を、利用者の困りごとに結びつけて確定する。
- **決めること**
  - スコープ(やる / やらない / いつかやる。全体の境界)
  - 優先度
  - **品質の優先順位**(例: 止まらないこと、誤って見せないこと、変更しやすいこと。何を優先するかの順位)
  - **受け入れ条件**(できたかどうかを判定する基準)
  - **権限・通知・個人情報を持つかどうかの「有無」**(詳細は P12・P13。ただし、有ると後のデータ項目に影響するので、有無だけはここで決める)
  - 公開に必要なもの(規約・プライバシー・不正への備え)の有無と、最低限の方針
- **決めないこと**: 実現手段、データの構造、画面の細部、権限・通知の詳細
- **成果物**: `dev_policy/05_要件.md`(確定したら `docs/` へ)
- **終わりの判定**: すべての要件が、どのストーリーに由来するかを辿れる。辿れない要件は削るか、理由を書く。
- **よくある失敗**: 「あったら便利」が、優先度を付けずに混ざる。有無を決めずに先へ進み、後でデータを作り直す。

### P6 業務フロー

- **目的**: 役割をまたいだ手順(誰が、いつ、何を、誰に渡すか)を、見える形にする。
- **決めること**: 利用者・運営者・システムの間の手順。特に、運営者が定常的にやる作業の一覧。
- **決めないこと**: データの形、画面、実現手段
- **成果物**: `dev_policy/06_業務フロー.md`
- **終わりの判定**: 運営の定常作業が洗い出され、P0 の制約(人数・運用期間)に収まるかを確認した。
- **よくある失敗**: 利用者側の流れだけを書き、運営側の作業を見落とす。

### P7 データ項目と状態

- **目的**: アプリの中心にある「もの」と「状態の変わり方」を、コードの前に確定する。
- **決めること**
  - **用語集**(同じものは同じ言葉で呼ぶ)
  - 覚えておく必要のあるデータ項目と、その関係。**具体的な値を入れた実例**を添える
  - **状態とその遷移**(どの状態から、どの操作で、どの状態へ移るか。表にする)
  - **見せ方のルール**(誰に、何を見せ、何を見せないか)
- **決めないこと**: 保存の仕組み、通信の形式、画面
- **成果物**: `dev_policy/07_データ項目と状態.md`(用語集、遷移表、見せ方のルールを含む)
- **終わりの判定**
  - 同じものに複数の呼び名がない
  - 遷移表を見れば、「ありえない状態」が書けないことがわかる
  - 見せ方のルールが、利用者ごとに1か所に書かれている
- **よくある失敗**: ルールが文章の中にだけあり、後でコードのあちこちに複製される。

### P8 画面設計(情報設計)

- **目的**: どの機能とデータを、どのページに載せるかを決める。**見た目の設計ではない。**
- **決めること**
  - ページの一覧。各ページの目的、載せる機能、載せるデータ項目
  - ページ遷移(どこからどこへ行けるか)
  - 空や失敗の状態に、何を伝えるか(見た目ではなく、内容)
  - URL の構造(公開して共有される前提なら、**一度公開した URL は変えない**のが原則)
- **決めないこと**: 配色、文字、余白、部品の見た目
- **成果物**: `dev_policy/08_画面設計.md`
- **終わりの判定**: P7 のすべてのデータ項目と、P4 のすべてのストーリーが、どこかのページに載っている。
- **よくある失敗**: 見た目の話が混ざる。データが載らないページや、どこにも載らないデータができる。

### P9 層の設計

- **目的**: 段階的に作れる「玉ねぎの層」を設計する。MVP を切る前に、全体の層構造を見えるようにする。
- **決めること**
  - 層の一覧。各層に、次を書く。
    - **利用者に起きる変化**(1文)
    - その層に含む機能・ページ・データ項目
    - **前提となる層**(依存)
    - その層で増える、運営の作業
  - 依存の図(内側の層なしに、外側の層は出せない)
- **決めないこと**: **技術に関することは、一切書かない。** 技術名はもちろん、実現手段や、技術的な土台(§9 の IFM でいう AE)も書かない。
- **書き方のルール**
  - 層は**価値の層**(縦切り)にする。「データ層・通信層・画面層」のような水平の層にしない。水平の層は、全部できるまで誰にも使えない。
  - 依存は、**機能・データ・利用者の状態の言葉**で書く(「〜できることが前提」という形)。
  - 技術的な土台は、P15 で技術を選んだあとに洗い出し、**必要になった層に割り当てる**。そのとき、層の定義は変えない。
- **成果物**: `dev_policy/09_層の設計.md`
- **終わりの判定**
  - どの層も、それだけで利用者が使える
  - 依存に循環がない
  - 切れるのは「内側から連続した範囲」だけ、という図になっている
- **よくある失敗**: 技術の都合で層を決める。依存を書かずに、思いついた順に並べる。

### P10 MVP の決定

- **目的**: 層のどこで切るかを決める。
- **決めること**
  - 切る位置。基準は、**P0 の成功の定義を満たす最小の範囲で、かつ、運営の作業(P6・P9 で洗い出したもの)が P0 の制約(人数・運用期間)に収まること**。
- **決めないこと**: 技術の選定、技術的な実現性の確認(P15 で行う)
- **注意**: この時点では、費用などの技術的な実現性を確かめない。そのため、**P15 で「この範囲は制約の中で成り立たない」と分かったら、手戻りのルール(§5)で P10 を見直す**。この見直しは失敗ではなく、あらかじめ想定した手順である。
- **成果物**: `dev_policy/10_MVP.md`
- **終わりの判定**: 切る位置の理由が、P0 の成功の定義と制約に結びついている。
- **よくある失敗**: 機能の個数で切る。

### P11 拡張の余地の確認

- **目的**: まだ作らない外側の層を、内側の設計が塞いでいないかを確かめる。**作るのではなく、塞がないこと。**
- **決めること**: 外側の各層について、「塞いでいない」か、「内側のこれを直す」かの確認結果
- **決めないこと**: 将来のための抽象化や、使わない仕組みの先行実装
- **成果物**: `dev_policy/11_拡張の余地.md`
- **終わりの判定**: 外側のすべての層について、確認結果が書かれている。直すものがあれば、手戻りのルール(§5)で P7・P8 を直した。
- **よくある失敗**: 「将来のため」に、今は要らない仕組みを作り込む。

### P12 権限設計 / P13 通知設計

P5 で「有り」とした場合だけ行う。「無し」なら、飛ばす。

- **P12 権限設計**
  - 決めること: ロールごとに、何を見られ、何を操作できるか。P7 の「見せ方のルール」との整合
  - 決めないこと: 認証の方式(P15 で決める)
  - 成果物: `dev_policy/12_権限設計.md`
- **P13 通知設計**
  - 決めること: どんなときに、誰に、何を伝えるか。個人情報の扱い
  - 決めないこと: 伝える手段(P15 で決める)
  - 成果物: `dev_policy/13_通知設計.md`
- **よくある失敗**: 有無を決めずに、後から足して、データと画面を作り直す。

### P14 見た目の設計

- **目的**: 見た目の規則を決める。P8 で決めた「何を載せるか」に、どう見せるかを与える。
- **決めること**: 配色、文字、余白、部品の見た目の規則。各ページのレイアウト
- **決めないこと**: 載せる機能やデータの追加(P8 に戻って決める)
- **成果物**: `dev_policy/14_見た目の設計.md`
- **終わりの判定**: すべてのページに、レイアウトが与えられている。
- **よくある失敗**: 見た目を決めている途中で、機能を足してしまう。
- **メモ**: P15 と並行して進めてよい。

### P15 技術選定

- **目的**: ここで初めて、要件を満たす手段を選ぶ。
- **決めること**
  - 言語・フレームワーク・保存先・動かす場所
  - コードの置き方(機能ごとにフォルダを分ける、など)
  - テストの種類と、何をテストするか
  - **技術的な土台(AE)の洗い出しと、各層への割り当て**(必要になった層で作る)
  - **実現性の確認**: P10 で決めた MVP の範囲が、P0 の制約(費用・人数・運用期間)の中で、選んだ技術で成り立つかを確かめる。成り立たなければ、P10 に戻って範囲を見直す(§5)
  - **それぞれの選定理由と、却下した案**
- **決めないこと**: 「将来あるかもしれない」ための抽象化(必要になってから足す)
- **成果物**: `dev_policy/15_技術選定.md`(決定記録 §4 の形式で)
- **終わりの判定**: すべての選定理由が、P5 の要件のどれを満たすためかに結びついている。P10 の MVP の範囲が制約の中で成り立つことが確認されている(成り立たない場合は、P10 を見直した)。
- **よくある失敗**: 慣れている技術を先に決め、要件を後から合わせる。

### P16 貫通

- **目的**: 最小の1操作を、端から端まで通して、全体がつながることを確かめる。
- **決めること**
  - 貫通させる1操作はどれか(最内層の中から選ぶ)
  - **外とのやり取りの形**(画面と裏側の間のデータの形、エラーの種類)。**実例のファイル**で示す
- **決めないこと**: ほかの機能、見た目の仕上げ
- **成果物**: 動くコード、テスト1本、CI(自動チェック)、`docs/契約/`(実例ファイルと説明)
- **終わりの判定**: 実際の環境で動き、テストが通り、他の人が手順書だけで起動できる。
- **よくある失敗**: 最初から多機能にして、つながるまでに時間がかかる。文章の仕様書だけがあり、実例が無い。

### P17 縦切りで機能追加

- **目的**: P9 の層を、内側から1つずつ足していく。
- **決めること**: 次に足す層(P9 の依存の順に従う)
- **決めないこと**: 複数の層の同時着手
- **成果物**: 機能ごとの PR
- **ルール**
  - 1機能 = 1フォルダ。既存のフォルダに別の機能を混ぜない
  - 共通化は**3回目**に出たときにする(2回なら待つ)
- **終わりの判定**: その層の受け入れ条件(P5)を満たす。
- **よくある失敗**: 似ているからと、早すぎる共通化をする。

### P18 品質確認

- **目的**: 実際に使う条件に近い形で、通しで確かめる。
- **決めること**: 確認する条件(人数、端末、回線)、失敗したときの動き
- **成果物**: `dev_policy/18_リハーサル記録.md`
- **終わりの判定**: P5 で決めた「品質の優先順位」の上位から順に、基準を満たしている。
- **よくある失敗**: 正常な場合だけを確かめて、失敗の場面を確かめない。

### P19 運用と振り返り

- **目的**: 使った結果から学び、次に活かす。
- **決めること**: 運用手順、振り返りで得た教訓
- **成果物**: `dev_policy/19_振り返り.md`。**必要ならこのマニュアルを更新する。**
- **終わりの判定**: 「次に同じものを作るなら、順序をどう変えるか」が書かれている。

## 4. 決定の記録

### 書き方(軽量版)

決定が出るたびに、次の5行を書きます。長くしません。

```
## 決定: (一言で)
- 状況: なぜ決める必要が出たか
- 決定: 何に決めたか
- 理由: なぜそれにしたか
- 却下した案: 何を、なぜやめたか
- 見直す条件: どうなったら決め直すか
```

### 置き場所の2層

| 場所 | 内容 |
|---|---|
| `dev_policy/` | **検討の過程**。途中の考え、TODO、まとめ役の作業用 |
| `docs/` | **確定版**。メンバーに配る完成した文書 |

この2つを混ぜません。確定したものだけを `docs/` に上げます。

---

## 5. 手戻りのルール

前のフェーズの決定を変えたくなったときは、次の順で進めます。

1. **決定の記録に、変更の理由を追記する**(消さずに、履歴を残す)
2. **その決定に依存する後ろの成果物を、すべて洗い出す**
3. **前から順に直す**

「気づいたら直す」は、大事な習慣です。ただし、**黙って直さず**、必ず記録します。

手戻りが起きやすい箇所は、次のとおりです。
- P9 の層の設計で、P7(データ)や P8(画面)の直しが見つかる。
- P15 の実現性の確認で、P10 の MVP の範囲を見直す(必要なら P9 の層の切り方も)。

## 6. 作業のルール

- `main` に直接 push しない。ブランチ → PR → レビュー → squash merge。
- 1つのPRは、1つの目的だけにする。
- 「整える変更」(動きを変えない)と「変える変更」(動きを変える)を、同じPRに入れない。
- **このリポジトリは公開です。** 秘密情報(鍵・トークン)、本番のデータ、個人情報を、絶対にコミットしない。

## 8. このマニュアルが生まれた理由

前作の[quizApp](https://github.com/NUTFes/quizApp)では、「仕様書(文章)→ 型 → 画面 → 遷移はハンドラの中に都度書く」の順で進めました。その結果、次のことが起きました。

- 状態の名前と、それに応じた分岐が、複数のファイルに散らばった。
- 「誰に何を見せるか」のルールが、2つの言語で二重に書かれた。
- 状態の遷移ルールが、文章にしか存在しなかった。

どれも、**決める順番**の問題でした。ルールを先にコードとして取り出していれば、避けられたはずです。このマニュアルは、その反省から作っています。

## 9. 参考にしたモデル

「機能の依存関係を考えて、段階的に作る順序(層)を決め、そのあとで MVP を切る」という考え方の参考にしたものです。

### 一覧

| 名前 | 提唱者 | 要点 | このマニュアルとの関係 |
|---|---|---|---|
| **IFM**(インクリメンタル・ファンディング法) | Mark Denne、Jane Cleland-Huang | 価値の最小単位(MMF)を、技術の前提(AE)と依存を考慮して並べる | **骨組みとして借りる**(下記) |
| ユーザーストーリーマッピング | Jeff Patton | ジャーニーを背骨に、ストーリーを並べ、横に切ってリリースにする | 層のどこで切るかの考え方 |
| ウォーキングスケルトン | Alistair Cockburn | 最小の機能で、端から端までつなぐ | 最内層の考え方 |
| ワードリー・マップ | Simon Wardley | 利用者のニーズから、必要な能力への依存の連鎖を描く | 依存を見える化する道具に近い |
| 依存構造マトリクス(DSM) | Donald Steward | 依存関係を行列にして並べ替える | 機能が多いときの依存の整理 |
| 製品の5層モデル | Theodore Levitt、Philip Kotler | 製品の価値を、中核から外側へ層で捉える | 玉ねぎの比喩に近い(ただし依存ではなく価値の段階) |
| SLC | Jason Cohen | MVP の代わりに、Simple・Lovable・Complete を基準にする | 公開向けの、「最小」の別の基準 |
| オニオン・アーキテクチャ | Jeffrey Palermo | コードの構造(依存を内側に向ける) | **名前は似ているが別物**(開発の順序の話ではない) |

IFM 以外は、提唱者名と概要を記憶から書いたもので、**出典は確認していません**。引用するときは、一次資料を確かめてください。

### IFM の要点

ソフトウェアを、利用者にとって価値のある最小の単位に分け、依存関係と投資対効果を見ながら、出す順番を決める方法です。開発プロセスそのものではなく、既存の進め方に重ねて使うものとして紹介されています。

| 部品 | 意味 |
|---|---|
| **MMF**(Minimum Marketable Feature) | 単体で利用者に価値が出る、最小の機能のまとまり |
| **AE**(Architectural Element) | MMF を作るために先に要る土台の部品。必要になったときに、必要な分だけ作る |
| **MMF 前後関係グラフ** | 「Aの前にBが要る」という関係の図。前提は、ほかの MMF のことも、AE のこともある |
| **並べ方の戦略** | 貪欲法、単純な先読み、重み付き先読み(書籍の目次による) |
| **指標** | 正味現在価値(NPV)、ROI、初期投資、自己資金化までの時間 |

核になる考え方は、**MMF の合計価値が、実装する順序に大きく左右される**ことです。AE を必要なときだけ作ることで、最初の投資も減らせます。

#### このマニュアルでの読み替え

| IFM | このマニュアル |
|---|---|
| MMF | 価値の層(P9。利用者が使える最小単位) |
| AE | 技術的な土台。**P9 では書かず**、技術選定(P15)のあとで洗い出し、必要になった層に割り当てる |
| 前後関係グラフ | 層の依存の図(P9。機能・データ・利用者の状態の言葉で書く) |
| 収益・NPV で並べる | P0 の成功の定義と、費用・運用の制約で切る(P10) |

IFM は本来、お金の流れで順序を決める方法です。収益のないプロジェクトでは、NPV や ROI の指標はそのまま使えません。**価値の単位・前後関係という考え方だけ**を借ります。IFM は MMF と AE を一緒に並べますが、このマニュアルでは、**層(価値)を先に決め、AE(技術)を後から割り当てる**順に分けています。
